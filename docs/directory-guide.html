0. 全体像

このリポジトリは 4つの動詞でできている。 作る（src）→ 測る（verification）→ 答え合わせする（replay_analysis）→ 記録する（docs）。

pokemonabc/ ├── CLAUDE.md セッション起動時の規約。playbook.md の読了を強制する ├── src/ 75MB 提出物そのもの（デッキ × パイロット） ├── verification/ 1.5MB 出す前に測るツールボックス ├── replay_analysis/695MB出した後に検死する解析室 ├── docs/ 1.0MB 意思決定ログ + レポート原稿（＝成果物） ├── .claude/ スキル / サブエージェント / ワークフロー定義 └── submission_*.tar.gz 提出済みアーカイブ（gitignore）
この構造を生んだ発見

D27:ローカルの自己対戦は自分に甘い（族内ベンチは相手操縦者との実力差に比例して +8〜+62pt 過大評価する）。この一点が、verification/ に較正の仕組みを、 replay_analysis/ に本番検死を、docs/ に主張台帳を要求した。 3ディレクトリすべてが同じ問題への対処になっている。

src/ 75MB / 13デッキ

提出物置き場。エージェント ＝ デッキ（60枚）× パイロット（main.py）なので、 1実験 = 1ディレクトリ。パスが src/input/datasets/decks/ なのは Kaggle 側の /kaggle/input/... を模しているから。

src/input/datasets/decks/starmie-clockguard/ ├── main.py 42KB agent(obs) -> list[int] を返す本体 ├── deck.csv 259B 60枚のカードID ├── cg/ ゲームエンジン（C製 libcg.dylib/.so/.dll + ctypes ラッパ） ├── GATES.md このデッキが通した受入基準の記録 └── run_acceptance.sh + acceptance_*.log

replay_analysis/ 695MB / 出した後に検死する

Kaggle 本番（実ラダー）の試合記録をダウンロードして解剖する検死室。 リプレイは https://www.kaggle.com/competitions/episodes/{id}/replay.json で公開されている。

なぜ必要か。ローカルが信用できないなら、本物の対戦記録だけが真実になるから。 作戦文書は「免許表」としてこう定めている：

問い測ってよい場所
勝率の絶対水準（±19pt）本番のみ（T1）
勝率の相対差 ±2〜4ptどちらも不可（常に明記する）
1手あたりの思考時間本番のみ（ローカルは 5.4倍 楽観と実証済み）

__pycache__/ — 気にしなくていいもの

Python が .py を実行する際に自動生成するバイトコードのキャッシュ。 作ったものでもデータでもない。gitignore 済みで、消しても次回実行時に再生成される。

ひとつだけ読み取れる情報がある — ここに .pyc がある5本（damage_accuracy / damage_pairing_diff / extract_decks / prize_race / trace_replay）は 他のスクリプトから import された＝部品として再利用されているということ。

eps〇〇/ — 提出1本ぶんのリプレイ倉庫

〇〇 は Kaggle の提出ID（submission ID）。 eps55163442/ なら「提出 #55163442 が実ラダーで戦った試合を全部集めた箱」。

eps55163442/ 123MB ├── curl.cfg ダウンロード指示書（URL一覧） ├── curl_new.cfg 追加分（後から到着した試合） ├── ep89334624.json 1試合ぶんの完全な記録（2.0MB） ├── ep89334721.json 3.7MB └── ... 約48試合
ディレクトリ中身サイズ
eps54943911/lucario-calib（較正提出）136MB
eps54961048/王者再提出 #2157MB
eps55058443/王者再提出 #3154MB
eps55060473/dragapult-calib8KB（meta.txt のみ）
eps55163442/P1 clockguard 進行中123MB
eps55169074/P2 widthprobe 進行中125MB

JSON 1本の中身はこうなっている：

top keys: ['configuration','rewards','statuses','steps', ...] steps: 85 85ステップ = 試合の全経過 rewards: [1, -1] 我々の勝ち statuses: ['DONE','DONE'] どちらもクラッシュせず完走

各 step にその瞬間の盤面（observation.current）と、実際に選んだ手（action）が 丸ごと入っている。だから「あの局面で何を選んだか」を後から完全に再現できる。これが検死の材料。

本体は meta.txt の方

eps55060473/ が 8KB しかないのに注目。JSON 本体は捨ててあり、レシピだけが残っている。

meta.txt: 88652311:0:1:SELF, 88652365:0:-1:53853843, 88652869:1:1:54990484, ... 試合ID :席:勝敗:相手の提出ID

.gitignore の記述：「検死用リプレイJSON本体（1提出あたり約150MB）。公開エンドポイントから 再取得でき、meta.txt + autopsy_*.py があれば検死は完全に再現できるので追跡しない。」
→ 695MB のうち Git に入っているのは実質ゼロ。重いデータはレシピに圧縮して保存する設計。

誰がどう見るか：人間は直接開かない（2〜4MB の JSON が50本）。 読むのは常にスクリプト経由で、Claude が解析を走らせて要約を docs/memo/data.md に書き込む。 あなたが目にするのはその要約。例外は trace_replay.py で、これだけは人間が1試合を物語として読むための道具。

測定結果 → writeup への直通路を意図的に塞いで、必ず証拠グレードのラベル付けを通す。 ラベルは 確証 / 弱確証 / 探索的 / 撤回・格下げ済 の4段階で、 各主張に「writeup でどう書くか」まで指定してある。

  • 「確証された改善とは書かない」（台帳#5）
  • 「n=3 の外挿であることを明記。『法則』でなく『3アーキタイプで一致した観測』と書く」（台帳#1）
  • 「v3棄却は正しかった、と断定しない」（台帳#12）

実際にこれで +15.7pt（事後選択値）などの格下げが機能した。
