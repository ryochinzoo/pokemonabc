0. 全体像

このリポジトリは 4つの動詞でできている。 作る（src）→ 測る（verification）→ 答え合わせする（replay_analysis）→ 記録する（docs）。

pokemonabc/ ├── CLAUDE.md セッション起動時の規約。playbook.md の読了を強制する ├── src/ 160MB 提出物そのもの（デッキ × パイロット）＝ 作る ├── verification/ 30MB 出す前に測るツールボックス ＋ 練習相手（他人のagent） ├── replay_analysis/9.5GB出した後に本番の対戦記録で検死する解析室 ├── docs/ 1.9MB 意思決定ログ + レポート原稿（＝賞金部門の成果物） ├── docs-for-you/ NotebookLM 投入用に厳選した素材セット ├── .claude/ スキル / サブエージェント / ワークフロー定義 └── submission_*.tar.gz 提出済みアーカイブ（gitignore）
この構造を生んだ発見

D27:ローカルの自己対戦は自分に甘い（族内ベンチは相手操縦者との実力差に比例して +8〜+62pt 過大評価する）。この一点が、verification/ に他人のエージェントを、 replay_analysis/ に本番検死を、docs/ に主張台帳を要求した。 3ディレクトリすべてが同じ問題への対処になっている。詳細は §3。

src/ 160MB / 30デッキディレクトリ

提出物置き場。エージェント ＝ デッキ（60枚）× パイロット（main.py）なので、 1実験 = 1ディレクトリ。パスが src/input/datasets/decks/ なのは Kaggle 側の /kaggle/input/... を模しているから。

src/input/datasets/decks/deckswap-tarountula-pilotfix/ ├── main.py agent(obs) -> list[int] を返す本体＝「パイロット」 ├── deck.csv 60行、1行1カードID＝「デッキ」 └── cg/ ゲームエンジン（C製 libcg.dylib/.so/.dll + ctypes ラッパ） ※ バイナリは gitignore。無ければ sample_submission からコピー
デッキディレクトリに置いてはいけないもの

ここは提出時にそのまま tar される場所。トレース *.jsonl やログを置くと 提出物に混入する（2026-08-08 に v2 ディレクトリから 8本8.4MB を退避した）。 測定の出力は scratchpad か docs/memo/ へ。

30デッキ・16グループ — 「それぞれ別のロジックなの？」への答え

半分近くは main.py がバイト単位で同一。 md5 -q */main.py | sort | uniq -c で数えると 30ディレクトリが 16グループになる。

main.py の md5行数本数正体
725ef4c9…94812王者パイロット。starmie-aggro が原本で、そのバイト同一コピー
3f55780b…11424pilotfix パイロット（ロケット団修理版）。今ラダーに載っている腕とその派生
残り14グループ各 1固有ロジック（下の表で個別に説明）
なぜコピーが16本もあるのか — これは散らかりではなく実験設計

このプロジェクトの測定は「変数を1個だけ動かす」ことで成立している。だから2種類のコピーが生まれる：

  • デッキ実験（deckswap-* / deckcand-*）＝ main.py を1バイトも変えずにコピーし、deck.csv だけ差し替える。 → 差が出たら、それはデッキの効果
  • パイロット実験（-pilotfix / -toolfix / -v2）＝ deck.csv を固定し、main.py だけ変える。 → 差が出たら、それは操縦の効果

2026-08-08 の実ラダー対照実験がこの形の完成例：deck.csv が a246be4f でバイト同一、 main.py だけ 725ef4c9（素）→ 3f55780b（修理版）に差し替えた2提出を、 本番ラダーで走らせて比べた。

デッキ合法性 — 2026-08-03 に前版の記述を撤回した

このガイドの前版（2026-08-02）は「同名4枚制限をエンジンは検査しない（6枚入りを受理する）」と 書いていた。これは falsified。 実測し直した結果、 battle_start(...).errorType は違反を返す：

  • 2 = コピー数違反（同一IDが5枚、同名を共有する2種で合計6枚、特殊エネ>4）
  • 3 = たねポケモン不在　／　4 = ACE SPEC違反（種類が違っても2枚はダメ）

違反デッキは errorPlayer >= 0 になり、ランナーがエージェントを INVALID と判定 → reward −1。つまり不正なデッキは「無視される」のではなく試合を落とす。 検査には verification/conformance.py を使う（このパスを既に呼んでいる）。
未追随 verification/README.md:100 にも同じ旧記述が残っている（T8案件）。

対戦の呼び出し連鎖 — 「実際にどう戦わせているのか」

新しいデッキを測るとき、走るのはこれだけ：

# 自分のデッキディレクトリ（main.py + deck.csv + cg/ がある場所）に入って呼ぶ cd src/input/datasets/decks/deckswap-tarountula-v2 REPO=/Users/yujiinoue/Documents/products/pokemonabc # ① 安全ゲート（相手＝ランダム。攻撃的な相手は自滅バグを隠すので必ず先に） python3 $REPO/verification/bench.py 120 # ② 本番の測定（相手＝他人が書いた実物のエージェント） python3 $REPO/verification/bench.py 200 \ --opponent $REPO/verification/reference/alakazam_ryota_agent.py \ --opponent-deck $REPO/verification/decks/ryota_alakazam_2026-07-05.csv

裏で起きていること。1プロセスの中で、我々の agent() と他人の agent() が交互に呼ばれるだけ：

なぜ並列で回してはいけないか

CEW — 採否を決める1個の数字

CEW = 較正済み遭遇加重合成指標。族外ゲージ各面の勝率を、 実ラダーでその相手に当たる確率で加重して1本にまとめたもの。 計算は必ず verification/cew.py を通す（手計算だと重み1個の付け忘れで採否が反転しうるため）。

CEW = Σ(重みᵢ × 勝率ᵢ) / Σ(重みᵢ) cew.py:87-92 現行の重み（2026-08-09 T3再較正・第2版。出典: 800-1099帯の実フィールド構成 側 n=6,341・自チーム除外 / 斥候72体・4,263エピソード） alakazam (フーディン) share 29.2% → 0.3399 grimmsnarl (オーロンゲ) share 19.3% → 0.2247 crustle (イワパレス) share 13.5% → 0.1572 lucario (メガルカリオ) share 13.2% → 0.1537 archaludon (ブリジュラス) share 10.7% → 0.1246 覆域 85.9% を再正規化 基準線 59.70 = いまラダーに載っている腕（pilotfix）のセル実測を新重みで合成 閾値 +2pt ※「魔法の壁」ではない。CI を必ず併記する 配分 Neyman 合計 N=3,200 80%検出力の MDE 1.87pt
重みは古びる。実際に大きく狂っていた

2026-08-09 の再較正で、旧重み（2026-07-26）がどれだけズレていたかが判明した： Lucario 3.4倍 / Archaludon 3.2倍 / Dragapult 7.4倍の過大、 Abomasnow に至っては 800-1099帯の census に1体も出現しないのに 5.6% の重みがあった。 逆に実シェア最大の フーディン(29.2%) と イワパレス(13.5%) は重み0で入っていなかった。 総Nを変えずに配分を直すだけで MDE が 2.67pt → 1.87pt に 30% 改善した ——ズレていたぶんが、そのまま検出力の損失だった。

3. なぜセルフ対戦をやめたのか このプロジェクト最大の教訓

よくある誤解を先に潰しておく。捨てたのは「自分のパイロットが、相手のデッキも動かす」測り方であって、 「自分のデッキ同士」ではない。そして置き換えたのは「我々が書いた別のデッキ」ではない —— それこそが捨てた側。

第1幕 / 6-28 D5
「速いから測れる」

selfplay.py を採用。9ms/戦で何千戦も回せる。だが介入が7件連続で棄却される。 ローカルではブリジュラスに 82% 勝っているのに、実ラダーでは 20%。

第2幕 / 7-21 D27
「計器が壊れていた」

デッキを固定して操縦者だけ入れ替えたら、族内 82% / 族外 20% / 実ラダー 20%。 族内は 62pt 過大評価、族外は誤差2pt以内で本番を予測した。

第3幕 / 8-02 D61 →
「その計器にも嘘があった」

外部摂取(T5)が1ヶ月止まっていたと発覚。公式Lucarioゲージが +45pt 甘いと判明し世代交代。 較正は一度やって終わりではなく、走り続ける保守作業だと分かった。

数字で見る — D61 の三段分解（N=300/腕）

測り方デッキパイロット勝率

→ デッキ差 7.0pt に対し、操縦者差 31.7pt。操縦者が 4.5倍効く。 相手のデッキリストを60枚完璧にコピーしても、それを動かすのが我々の下手なコードである限り無意味。 族内の甘さは相手操縦者と我々の実力差に比例する（steel +62pt / 公式Lucario +41pt / りょーちんagent +8pt）。

何が置き換わったのか（2層構造）

候補判定理由
(a) 我々が書いた別のデッキ✗ これが捨てた側 デッキをどれだけ正確にコピーしても、操縦者が我々なら +8〜+62pt 甘い
(b) 第三者のエージェント✓ 日々の判定 verification/reference/。速く何百戦も回せる。ただしこれ自体が仮説
(c) 実 Kaggle ラダー✓ 較正の錨 replay_analysis/。遅く N=50〜60 しか取れないが、これだけが真実。 (b) が正しいことを (c) で確認して初めて「較正済み」と呼ぶ

セルフ対戦は「廃止」ではなく「格下げ」

いまも使う。ただし用途が限定されている（playbook §7.5 の層S）：

  • 正当性の検査 — vs random ≥96% ／ CRASH=0 ／ 敵対的入力での robustness-guard
  • 機構の診断 — トレースで「ロケットラッシュが盤面何体で発射されたか」を見る
  • リファクタ無罪の証明 — 勝率ではなく決定の完全一致で証明する （169,430決定が 100.00% 一致）。勝率50%より強い証拠で、しかも数分で済む ——50%は「差を検出できなかった」に過ぎないが、完全一致は「差が無い」の直接証明

禁じられているのは「族内の勝率を採否判断や記事の看板数値にすること」だけ。

2026-08-08 — この規律を破ると何が起きるかの実例

「v2 デッキの差分は実質ゼロ（+0.04pt）」という記録は、重みに族内オーロンゲゲージを 19.3% 混ぜていたための誤りだった。 族外のみで再計算すると −2.70pt（符号が反転）。
同じ日、ローカル計器で +4.09pt と出た操縦者修理は、実ラダーの対照実験では +1.7pt・CI ほぼ完全重複だった。これは「効果が無い」ではなく 「この N ではそもそも +4pt は原理的に見えない」（覆域差のSE ≈ 13pt）という意味。

Kaggle 本番（実ラダー）の試合記録をダウンロードして解剖する検死室。 リプレイは https://www.kaggle.com/competitions/episodes/{id}/replay.json で公開されている。 .py は31本。
