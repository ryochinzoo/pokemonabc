Pokémon TCG AI Challenge

ポケモンカードゲームのシミュレーション対戦AIを構築し、最強のエージェントを目指すプロジェクト

そもそも何をするプロジェクト？

Kaggleで開催されている「Pokémon TCG AI Battle Challenge」というAIコンペティションのためのチーム開発用リポジトリです。

目的は、ゲームエンジンが提供する盤面状況を分析し、最も勝利確率の高い行動（技を使う、ベンチに出す、手札を増やすなど）を自動で選択し続ける最強の「AIエージェント」を開発することです。

エージェントの仕組み

このコンペティションにおける「エージェント」は、以下の2つの要素の掛け算で定義されます。

Agent = Deck (60枚のカード) × Pilot (プレイングAI)
🃏 デッキ (Deck)

どのカードを60枚入れるかの構築情報。強いカードの組み合わせを見つける戦略的アプローチです。

🧠 パイロット (Pilot)

配られた手札や盤面情報を見て、どう動くかの意思決定ロジック。`main.py` に記述します。

開発の基本ワークフロー

1
デッキとロジックの実装
`src/input/datasets/decks/` 内に新しい実験フォルダを作成。`deck.csv` でカードを組み、`main.py` にプレイングのルール（ヒューリスティック）を記述します。
2
ローカル検証＆ベンチ
`verification/` に移動し、`bench.py` や `selfplay.py` を実行。ランダムAIや歴代の強敵AI（gauge）と対戦させ、勝率とエラー（クラッシュ）がないかチェックします。
3
リプレイの分析
Kaggle上で動いている他のプレイヤー of 対戦ログ（リプレイ）を `replay_analysis/` を使って取得・分析。敵がどんなデッキを使っているかを暴きます。
4
評価と改善の記録
実験結果やアイデア、対戦環境のメタデータを `docs/memo/` に記録。勝率の推移や意思決定を整理し、次のサイクルへと繋げます。

プレイングAI (main.py) の基本形

AIプログラムである `main.py` は、ゲームエンジンと通信するための以下の構造（関数）を守る必要があります。

main.py Python 3.x
def agent(obs_dict: dict) -> list[int]:
    # 1. ゲーム準備段階: デッキを返す
    if obs_dict.get('select') is None:
        # デッキの60枚のカードIDリストを返す
        return [101, 101, 101, 101, 102, ...]

    # 2. プレイング段階: 提示された選択肢から選ぶ
    options = obs_dict['select']['option']
    min_count = obs_dict['select']['minCount']
    max_count = obs_dict['select']['maxCount']

    # 盤面（options）を評価して、選ぶアクションのインデックスを決定
    selected_indices = [0] # 例として最初の選択肢を選択

    return selected_indices

⚠️ 注意: AIがゲーム中に一度でも例外（クラッシュ）を起こしたり、無効なアクションを選択したりすると、即座に敗北（反則負け）となってしまいます！

チーム開発ルール

📊

提出前のローカルベンチマーク義務化

Kaggleにアップロードする前に、必ず `verification/` の評価テストを通してください。ランダムAIや基準AI（Gauges）と十分な数対戦し、勝率を測定するとともに、クラッシュ率が「0%」であることを確認します。

⌛

提出枠（バジェット）の節約

Kaggleへの提出は1日5回までに制限されています。さらに最終的な評価は「最新の2件」で行われるため、常に最もパフォーマンスの高い安定した2つのバージョンを残すように制御します。

🛡️

標準ライブラリの制限

Kaggleのサブミット環境に依存関係がないため、エージェントの実装 (`main.py`) は「Python標準ライブラリのみ」で行う必要があります。外部ライブラリを追加してはいけません。

🃏

デッキの枚数制限ルールは自主チェック

ゲームエンジンは「同名カードを4枚までしか入れてはいけない」というルールを自動で弾きません（6枚入れても動いてしまいます）。そのため、デッキを作成した際は自分たちで確認する必要があります。
