## 0. 最初に結論

**プロンプトの品質は高い。問題は「診断の質」ではなく、「診断から提出までの鎖が最後の1本だけ切れていること」。**

だから「もっと厳密にしろ」という指摘は1つもない。むしろ逆で、
**厳密さの投入先が偏っている**というのがこのレビューの主旨。

そしてこれから書くことの根拠のほとんどは、**りょーちん自身が監査レポートに書いた数字**。
外から持ち込んだ基準で殴るつもりはない。

## 1. まず、良い点（具体的に）

お世辞ではなく、方法論として真似すべき点が複数ある。

### 1-1. 勝利リプレイを対象に含めた

監査対象68件の内訳を `v7.3敗戦20 / v7.3勝利18 / v7.4敗戦18 / v7.4勝利12` と明示している
（`ptcg_68_replay_research_audit.md` 監査原則）。

「負けた試合だけ見て原因を探す」は、この手の分析で最も踏まれやすい罠。
それを踏まずに、しかも **§1.2 で「勝利ラベルはPolicy欠陥をかなり隠している」**
（対外29勝中12勝に確定損失、Attack終結26勝中9勝に確定損失）を
**自分で発見している**。これは対照群を置いたから出た結論で、置かなければ一生見えなかった。

### 1-2. 情報境界を「数えて」検証した

`ptcg_68_information_boundary_metrics.csv` で、相手の手札の中身・山札の並び・サイドの中身が
判断時点で `visible = 0` であることを実測している。

「未来情報を使っていないつもり」ではなく「使っていないことを数で示した」。
Strategy部門のレポートでそのまま証拠として使える品質。

### 1-3. 「不明」を埋めない規律が実際に機能している

§1.6 / §2.9 / §3.11 に「不明として残す事項」が実際に列挙されている。
プロンプトに書いたルールが**文章だけで終わらず出力物に反映されている**。

### 1-4. 事実 / 推測 / コード確認事項の三分離

`ptcg_68_dominance_audit_cases.csv` が
`confirmed_fact` 列と `unknown_or_limit` 列を分けて持っている構造は良い。
「同TurnのKOへ到達できた（確定）／KO後を含む将来盤面全体の優越までは証明していない（限界）」
という書き分けは、証拠の強度を正しく表現している。

## 2. 決定的な問題：鎖が切れている場所

プロンプト §7 の最終目標はこう定義されている。

> Replay分析 ➔ 異常分類 ➔ 頻度集計 ➔ コード原因特定 ➔ 最小修正 ➔ Replay比較 ➔ 勝率改善

**最後の矢印「Replay比較 ➔ 勝率改善」が、検証されないまま仮定になっている。**

### 2-1. 「修正後監査」は回帰チェックであって、勝率測定ではない

プロンプト §5-3 が要求しているのは
「目的以外の行動選択順位が変わっていないか」の比較。

これは**回帰チェックとしては非常に優秀**。
「Attach修正でBossの順位が動いたら新バグ候補」という発想は正しいし、
§3.10「修正後の回帰Guard」で
`変更されるべき経路` と `維持されるべき経路` を別々に列挙しているのは、
テスト設計として教科書的に正しい。

**ただしこれで確認できるのは「壊していないこと」だけで、「強くなったこと」ではない。**

現在のプロセスには次が全部ない。

| 欠けているもの | 無いとどうなるか |
|---|---|
| N（何戦回すか）の事前登録 | 良い結果が出るまで回してしまう |
| 勝率の信頼区間 | 偶然の±5ptを改善と誤認する |
| kill基準（効果が出なければ捨てる） | 効かない変更が永久に残り、コードが膨らむ |
| 対戦相手のばらつきの管理 | 相手が弱かっただけの数字を実力と誤認する |

つまり **改善したのか劣化したのか、本人にも分からないまま提出されている**。
レートが動かない最大の原因はここだと考えている。

### 2-2. りょーちん自身の数字が「Policy修正では届かない」と言っている

§1.5-3 にこう書かれている。

> 敗戦38件中19件には確定損失があるが、**勝敗反転まで証明できるのは現時点で1件のみ。**

これは非常に誠実な記述で、同時に**このレビューで一番重い数字**。

- 38敗のうち、Policy欠陥が原因で負けたと**証明できた**のは **1件（2.6%）**
- 残り37敗は、Policy修正で取り返せるという証拠が**まだ無い**
- §1.6 で「L4の19敗が、ドロー事故・構築相性・未発見Policy欠陥のどれに属するか」を
  **自分で「不明」に分類している**

「確定損失19件」と「勝敗が反転する19件」は全く別物で、
りょーちんはそれを混同していない。そこは正しい。

**問題は、それでも投入先がPolicy修正に100%集中していること。**
自分で「原因が不明」と書いた37敗に対して、
プロンプトは「Replayをもっと精読する」以外の打ち手を持っていない。

### 2-3. 感度分析の結果は「効く摘み」と「効かない摘み」を既に分けている

`ptcg_68_sensitivity_summary.csv` の37設定を集計すると：

| changed_nodes | 設定数 | 意味 |
|---:|---:|---|
| 0 | 12 | 値を動かしても行動が1つも変わらない |
| 1〜20 | 19 | ごく局所的にしか効かない |
| 133〜188 | 6 | **全体の約1割（約1,540 node中）を動かす** |

そして133以上を動かしているのは**すべて `HIGH_VALUE_PREP_MIN_LEGACY`**。

これは価値ある発見。**「摘みの効き目は桁で違う」ことが自分のデータで出ている。**
にもかかわらず、この情報が「じゃあ `HIGH_VALUE_PREP_MIN_LEGACY` を実測でチューニングしよう」
という次の行動に繋がっていない。**掃引はしたが、勝率で判定していないから採否を決められない。**
ここも 2-1 と同じ鎖の切れ方をしている。

## 3. 構造的な限界：この監査手順では原理的に答えが出ない問い

### 3-1. デッキの是非は、このコーパスからは出せない

§1.5-5 にこうある。

> 「現デッキを変えるべき」という証拠はこの項目からは出ていない。
> むしろ、攻撃終結型の勝利が多数あるため、Policy修正前にデッキを変更すると原因分離を失う。

**原因分離を優先する判断そのものは、科学的には正しい。**
ただし2点を指摘したい。

**(1) 「証拠が出ていない」のではなく「この方法では出せない」**

監査対象68リプレイは全部**同じデッキで戦った試合**。
同じデッキの試合をいくら精読しても、
「別のデッキならもっと勝てたか」という問いには**構造上絶対に答えられない**。
証拠が無いのは、デッキが良いからではなく、**そこを測る実験をしていないから**。

デッキの是非は、Replay監査ではなく **A/B測定**（同じパイロットで自陣デッキだけ差し替えて勝率比較）
でしか出ない。

**(2) こちらの実測では、デッキ差の効果量がPolicy修正より大きかった**

ゆうじ側の提出履歴（`docs/memo/data.md`）:

| 提出 | パイロット | デッキ | レート |
|---|---|---|---:|
| 2026-07-17 | v2.1 | Kangaskhan+Crustle | 650.2 |
| 2026-07-18 | v2.1b | Starmie rank9 | 625.7 |
| 2026-07-19 | v2.1c | Starmie rank9 | 718.6 |
| 2026-07-19 | v2.1c | **starmie-aggro** | **728.7**（瞬間最高804.7） |

パイロットをほぼ据え置いてデッキ側を動かした区間で **約100pt** 動いている。
これは「デッキを変えろ」という主張ではなく、
**「効果量の大きい変数を、一度も測らずに固定している」という指摘**。

締切まで19日という状況で、**最大の変数を測定対象から外したままなのはリスクが大きい。**

### 3-2. v7.3 と v7.4 の比較は交絡している

§1.6 に自分でこう書いている。

> 相手強度とマッチング分布がv7.3/v7.4で同等か（不明）

そのとおりで、v7.3 と v7.4 は**別提出・別時刻・別レート帯**で戦っている。
違うのはコードだけではなく、**当たった相手も違う**。

にもかかわらず、監査レポート全体（§1.2 のバージョン別表、§2.7-4 の Issue5差分評価など）は
v7.3 と v7.4 を並べて比較している。

**「交絡を認識しているのに、それでも比較して結論を出している」**のが問題。
こちらでも同じ罠を踏んで、後から記録に残している（`decisions.md` D27 / D29）。
これは能力の問題ではなく、**実測ハーネスが無いと構造的にこうなる**という話。
ローカルで同条件対戦ができれば、この交絡は最初から発生しない。

## 4. 原則と実装が正面から矛盾している箇所

プロンプト §2 原則3 はこう書かれている。

> 「Alakazam（フーディン）対策」のような特定カード固有の処理を追加しない。

しかし `main.py` には次がある（v8, `024cc99`）。

```python
# main.py:92-94
HAND_ALAKAZAM_LINE = {741, 742, 743}
COUNTER_ALAKAZAM_LINE = {109, 245}
ALAKAZAM_LINE = HAND_ALAKAZAM_LINE | COUNTER_ALAKAZAM_LINE

# main.py:175-179
"ALAKAZAM": {
    "main_axis": "FROSLASS_OPTIONAL",
    "must_pressure": ALAKAZAM_LINE,
    "boss_targets": ALAKAZAM_LINE,
},
```

**プロンプトが禁止事項の代表例として名指ししたものが、そのままコードに入っている。**
加えて `ACTIVE_FROSLASS_WATER_FLAT_BONUS` / `STARMIE_WATER_MARGINAL` という
カード名入りの調整定数も感度分析の対象になっている。

これは「ルール違反だから直せ」という指摘ではない。
**原則の方が広すぎる**というのがこちらの見解。

- **自分の60枚に対するカード固有処理は、過学習ではない。** デッキは固定で中身が既知なので、
  「Mega Starmie ex に水エネを貼ると何が解禁されるか」を書くのは単に**正しいプレイの記述**
- **相手に対するカード固有処理は、条件付きで正当。** ただし
  「そのアーキタイプに実際どれくらい当たるか」の遭遇率を根拠にすべき

現状の全面禁止は、**守ると弱くなり、破ると原則が形骸化する**という二択を強いている。
実際いま起きているのは後者。改良版では
「禁止」ではなく **「遭遇率と効果量で正当化できるなら可」** という判定可能な条件に置き換える。

同様に **原則「最小修正を優先する」も実態と乖離している**。
§3.9-4 が要求しているのは
「到達可能な後続Attack、damage、KO、Prize、Winまで**経路として評価する**」という
**明確な構造変更**であり、v8 は実際 `main.py` に **+919行**を追加している。

最小修正と構造変更は**必要なゲートが違う**（後者は回帰リスクが桁で大きい）。
同じ原則で両方を扱おうとしているのが無理の原因なので、改良版ではレーンを分ける。

**止める条件を明示しない限り調査は止まらない。**

## 6. ハード要件がプロセスに入っていない

Kaggle側の絶対条件は3つ。**agentはクラッシュ禁止 / 常に合法手 / 手番制限時間内。**
違反した時点でその試合は無効＝負け扱いになる。

**現行の監査手順には、この3つを確認する工程が一切ない。**
そして実装側にも次の穴がある。

### 6-1. `agent()` に最上位 try/except が無い（`main.py:4019-4027`）

```python
def agent(obs, config=None):
    if not isinstance(obs, Observation):
        obs = to_observation_class(obs)
    if obs.select is None:
        return list(DECK)
    if obs.current is None:
        return []
    board = BoardView(obs)
    return choose_indices(board)
```

`main.py` 4,027行のうち `except` は**わずか4箇所**（45 / 261 / 272 / 653行目）で、
うち3つは初期化・デッキ読込まわり。

つまり `BoardView` / `Policy`（1,345行）/ `GameSimulator` のどこか一箇所でも
想定外の値で例外を投げたら、**そのまま試合が飛ぶ**。

4,027行・カード固有分岐multi・enum依存という構成を考えると、
「一度も例外が出ない」に賭けるのは分が悪い。
なお `CLAUDE.md` にも明記があるとおり、
**`cg/api.py` の enum は大会期間中にメンバーが増える可能性がある**ので、
「今動いている」は「来週も動く」を意味しない。

### 6-2. `choose_indices` が空リストを返しうる（`main.py:4003-4006`）

```python
def choose_indices(board: BoardView) -> List[int]:
    ranked = GameSimulator(board).rank_options()
    if not ranked:
        return []
```

`minCount >= 1` の場面でここに落ちると **不正選択**になる。
`rank_options()` が空を返す条件を確認し、返せないなら
「先頭のOptionを返す」等の安全側フォールバックが要る。

### 6-3. `_read_deck()` の2つの穴（`main.py:246-263`）

```python
deck = [int(line.strip().rstrip(",")) for line in file.read().splitlines() if line.strip()]
if len(deck) == 60:
    return deck
except OSError:
    pass
return list(DEFAULT_DECK)
```

- **`int()` の ValueError が捕捉されていない**（`except OSError` のみ）。
  deck.csv に数字以外の行が1つ混ざるとimport時にクラッシュし、agent自体が起動しない
- **60枚でないと黙って `DEFAULT_DECK` に落ちる**。
  デッキを差し替えたつもりが**旧デッキで戦い続ける**。ログもエラーも出ない

**現時点では発火していない**（v8の `deck.csv` は彼自身のパーサで60枚ちょうどに読めることを確認済み）。
ただしデッキを頻繁に差し替える運用なので、いずれ踏む。

### 6-4. 「本番でだけ全敗する」経路が未検査

こちら側で発見した事象（`decisions.md` D37）:

> **`agent()` のデッキ返却経路は、他のどのツールでも実行されない。**
> 壊れていても全数値は正常に出て、本番だけ全敗する。

`obs.select is None` のときに60枚を返す経路のこと。
ローカルの自己対戦は `deck.csv` を直接エンジンに渡すので**この経路を通らない**。
つまり **「ローカルでは全部正常なのにラダーでレートが上がらない」の典型症状**であり、
りょーちんの症状と一致する。

エンジンはデッキエラーを検査しており
（`battle_start` の `start_data.errorPlayer >= 0` → 本番 `INVALID` = 即敗北）、
一方で**同名4枚制限は検査しない**（5枚でも通る）。
この非対称性は事故を起こしやすい。

**優先度としては、§2〜§5 の話より先にこの §6 を潰すべき。**
上限を作っているのがここなら、Policyをどれだけ磨いても頭打ちになる。

## 8. 渡せる道具（Codex前提）

りょーちんは Codex を使っているので、こちらの `verification/` がそのまま通じるかを確認した。

**結論: 中身は素のPython3スクリプトなので、無改造で動く。**

```bash
# デッキディレクトリで実行する
python3 <repo>/verification/bench.py 300          # 対ランダム勝率＋95%信頼区間
python3 <repo>/verification/conformance.py        # 本番ランナー適合検査（§6-4対策）
python3 <repo>/verification/donk_meter.py 400 ... # 序盤即死率
```

Claude固有なのは**外側のラッパーだけ**なので、そこは剥がして渡す。

| Claude方言 | Codex側での置き換え |
|---|---|
| `/bench` `/try-heuristic` `/submission-check` | 生のシェルコマンドに書き下す |
| `CLAUDE.md` | Codex が読むのは **`AGENTS.md`** |
| `.claude/agents/robustness-guard` | 手順として文章に展開 |
| `playbook.md` を読め、という参照 | 必要な規律をプロンプト本文に直接埋め込む |

### 重要：渡してはいけない層がある

`verification/README.md` に明記されているとおり、

> ※CEWの重みは現在の帯の実遭遇分布に紐づく。帯が変われば再計算する

こちらの採否基準 **CEW** は **750〜820帯の遭遇率**
（Lucario 45.1 / Archaludon 33.8 / Dragapult 15.5 / Abomasnow 5.6%）から作られている。
りょーちんは **485〜570帯**で当たる相手が違うため、
**CEWをそのまま適用するのは方法論として誤り**。
`N=3,200` を真に受けると、残り19日を測定だけで溶かす危険もある。

したがって**2層に分けて渡す**。

**第1層 — 帯に依存しない。そのまま渡す**
- `conformance.py`（本番ランナー適合検査）
- `CRASH = 0`
- `vs random ≥ 96%`
- `bench.py`（勝率＋95%信頼区間）
- `donk_meter.py`（序盤即死率）
- 同名カード4枚以下の手動チェック（エンジンは検査しない）

**第2層 — 帯に依存する。渡さない、または彼の帯で再較正する**
- CEWの重み / 基準線 43.13% / 閾値 +2pt / Neyman配分 N=3,200

**現状の帯なら、第1層だけで足りる可能性が高い。**
§6-4 の症状と一致している以上、まず第1層で原因を切り分けるのが最短。
