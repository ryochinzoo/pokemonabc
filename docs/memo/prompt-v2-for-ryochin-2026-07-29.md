## §1. 目的

AIの対戦リプレイに対する感想の記述ではなく、
**「勝率に最も影響するバグを証拠付きで特定し、最小変更で修正し、実測で採否を決めること」**を目的とする。

v1 からの変更点は末尾の「**実測で採否を決める**」。
「見つけて直した」で終わらせず、**強くなったことを数字で確認してから採用する**。

- **注意:** 監査（Replay分析）段階では**コード修正を行わない**。
- **注意:** 実測なしにコードを採用しない。**測らずに提出しない。**

## §2. 核心原則

### 原則1：Replayの客観的事実を最優先 ＜v1から変更なし＞

Replayから明確に確認できる「事実」のみを記述する（主観・感情的評価・推測は排除）。

- 〇 適切: `Turn7で合法Attachが存在` / `実際はAttackを選択` / `Attackの実ダメージ0`
- ✕ 不適切: `Attachすべきだった` / `勝てたはず` / `AIが馬鹿`

### 原則2：事実と推測の完全分離 ＜v1から変更なし＞

1. **Replay事実**（観測された結果）
2. **推測**（反実仮想・仮説）
3. **コード確認事項**（確認すべきロジック）

### 原則3：カード固有処理は「禁止」ではなく「正当化を要求する」 ＜v2で書き換え＞

**v1の記述（全面禁止）は運用できていなかったため改訂する。**

v1 は「Alakazam対策のような特定カード固有の処理を追加しない」と定めていたが、
現行 `main.py` には次が存在する。

```python
# main.py:92-94
HAND_ALAKAZAM_LINE = {741, 742, 743}
COUNTER_ALAKAZAM_LINE = {109, 245}
ALAKAZAM_LINE = HAND_ALAKAZAM_LINE | COUNTER_ALAKAZAM_LINE

# main.py:175-179
"ALAKAZAM": {"main_axis": "FROSLASS_OPTIONAL",
             "must_pressure": ALAKAZAM_LINE,
             "boss_targets": ALAKAZAM_LINE},
```

禁止事項として名指しされたものが実装に入っている以上、
**原則の方が広すぎる**と判断する。守れば弱くなり、破れば原則が死ぬ。

そこで**対象を2つに分けて、それぞれ別の基準を課す**。

| 対象 | v2での扱い | 根拠 |
|---|---|---|
| **自分の60枚**に対するカード固有処理 | **無条件で可** | デッキは固定で中身が既知。過学習ではなく単に正しいプレイの記述 |
| **相手のカード/アーキタイプ**に対する固有処理 | **条件付きで可**（下記3条件） | 相手は未知。当たらない相手への最適化は無駄かつ危険 |

**相手固有処理を入れてよい条件（3つすべて満たすこと）**

1. **遭遇率**: そのアーキタイプに実際どれくらい当たるかを、リプレイ本数で示せる
2. **効果量**: その処理の有無で勝率がどう動くかを、族外相手の実測で示せる（§5-4）
3. **退避性**: 該当アーキタイプ以外の対戦で、勝率が下がっていないことを確認できる

**満たせないなら、汎用化した表現に落とす。**
「Alakazam対策」ではなく「相手ポケモンの脅威度評価」として書けるなら、そちらを優先する。
汎用化はいまも推奨されるが、**それは目的であって禁止事項ではない。**

### 原則4：測定なき採用の禁止 ＜v2で新設＞

- 勝率を実測していない変更を、提出物に含めない
- 「順位が正しくなった」は**採用の根拠にならない**。それは回帰チェックの結果であって効果ではない
- 測定は**変更前と変更後を、同じ相手・同じN・同じ条件**で行う
- **別提出のラダーレート同士を比較しない**（相手分布が違うため交絡する）

### 原則5：調査は有限 ＜v2で新設＞

- すべての調査に**事前に時間上限を宣言してから着手する**
- 上限に達したら、結論が出ていなくても**「不明」として記録し、次へ進む**
- 「もっと調べれば確からしくなる」は常に真なので、**止める条件が無ければ止まらない**

### 原則6：最小修正を優先する ＜v1から範囲を限定＞

**ただしこれは「レーンB（最小修正）」にのみ適用する。**

到達可能な後続Attackまでを経路として評価する等の**構造変更は、そもそも最小修正ではない**。
構造変更を「最小修正」の名前で通すと、原則が形骸化する。
構造変更は**レーンC**として、より重いゲートを課したうえで実施する（§6）。

## §3. 監査手順

### STEP 0：ハード要件チェック ＜v2で新設・最優先＞

**Policyの議論を始める前に、必ずこれを通す。**

Kaggle側の絶対条件は3つ。**クラッシュ禁止 / 常に合法手 / 手番制限時間内。**
違反した時点でその試合は無効＝負け扱いになる。
ここが破れていると、Policyをどれだけ磨いても上限に張り付く。

```bash
cd src/input/datasets/decks/mega-starmie-ex-deck-ct

# 1. 本番ランナー適合検査
python3 ../../../../../verification/conformance.py

# 2. 対ランダムでクラッシュ検出＋下限確認
python3 ../../../../../verification/bench.py 300 --baseline 0.96

# 3. リポジトリ直下に戻ってプリフライト
cd ../../../../..
python3 .claude/skills/submission-check/scripts/check.py \
  --submission src/input/datasets/decks/mega-starmie-ex-deck-ct
```

**合格条件**

| 項目 | 条件 |
|---|---|
| `conformance.py` | `CONFORMANCE=PASS` |
| `bench.py` | `CRASH=0` かつ `GATE=PASS` |
| `check.py` | `exit 0`（FAIL 0件） |

**1つでも落ちたら、Replay監査より先にそれを直す。**

> **なぜ `conformance.py` が特に重要か**
> `agent()` は `obs.select is None` のとき60枚のデッキを返す。この分岐は
> **ローカルの自己対戦では一度も実行されない**（`deck.csv` を直接エンジンに渡すため）。
> 一方 Kaggle 本番の interpreter は `agent()` の戻り値をデッキとして使い、
> 60枚でなければ `INVALID` ＝ 即敗北にする。
> つまりここが壊れていると、**ローカルの全数値が正常なまま本番だけ全敗する**。
> 「ローカルでは良さそうなのにレートが上がらない」ときの第一容疑者。

> **既知の弱点**（現時点では発火していないが、いずれ踏む）
> - `agent()`（`main.py:4019`）に最上位 try/except が無い。
>   `BoardView` / `Policy` / `GameSimulator` のどこかで例外が出ると試合が飛ぶ
> - `choose_indices`（`main.py:4003`）が空リストを返しうる。
>   `minCount >= 1` の場面では不正選択になる
> - `_read_deck()`（`main.py:246`）は `except OSError` のみで **ValueError を捕捉していない**。
>   また60枚でないと**黙って `DEFAULT_DECK` に落ちる**（デッキを替えたつもりが旧デッキで戦う）
> - `cg/api.py` の enum は大会期間中にメンバーが増えうる。**網羅性を仮定しない**

### STEP 1：通読 ＜v1から変更なし＞

リプレイを途中で判定せず、必ず最初から最後まで通読する。

### STEP 2：ターン別記録 ＜v1から変更なし＞

各Turnについて最低限:
`Turn` / `自分盤面` / `相手盤面` / `合法Option` / `実選択` / `結果` / `次Turnへの影響`

### STEP 3：異常検出 ＜v1から変更なし＞

既知のIssueに無理に当てはめず、新しい異常パターンの定義を許容する。

*異常例:* Zero-damage Attack Preference / Attach即時価値不足 / Development Bias /
Retreat損失 / Opponent Threat無視 / Boss評価不足 / Energy貼り先異常

### STEP 4：同種異常の集計 ＜v1から変更なし＞

発生Replay数、総発生回数、初出Turn（序盤か終盤か）を記録・集計する。

### STEP 5：勝敗反転の見込みを分離して記録 ＜v2で新設＞

**「確定損失がある」と「それを直せば勝てた」は別物。混ぜない。**

各異常について次の3つを別々に数える。

| 区分 | 意味 |
|---|---|
| **確定損失** | その局面でより良い合法手があったことを、公開情報だけで確定できる |
| **勝敗反転（証明済み）** | それを直すと勝敗がひっくり返ることまで示せる |
| **勝敗反転（未証明）** | 直しても勝てたかどうか分からない |

そして最後に必ずこれを書く。

> **この異常を全部直した場合の、勝率改善の上限見積 = 「勝敗反転（証明済み）」の件数 ÷ 総敗戦数**

これが小さい場合、**その異常は優先度が低い**。
どれだけ件数が多くても、勝敗に効かないなら後回しにする。

> **v1実績での例**: 68リプレイ監査（`ptcg_68_replay_research_audit.md` §1.5-3）では
> 「敗戦38件中19件に確定損失があるが、**勝敗反転まで証明できるのは1件のみ**」だった。
> 上限見積 = 1/38 = **2.6pt**。
> これは監査の質の問題ではなく、**Policy修正で取り返せる幅がそもそも小さい**という発見。
> 残り37敗の原因（ドロー事故 / 構築相性 / 未発見欠陥）を切り分ける方が効果が大きい可能性がある。
> → その切り分けが**レーンD（デッキA/B）**。

## §4. 情報の切り分けとコード調査条件

### A. Replayのみで確定できること（事実） ＜v1から変更なし＞

- 0ダメージ攻撃を2回選択した / 合法Attachを選ばなかった
- Bossが合法プレイだった / Attack後に敗北した / Energyを失った

### B. Replayだけでは確定できないこと（推測・コード検証が必要） ＜v1から変更なし＞

- 勝てていたか / 最善手は何か
- 原因関数 / Tier問題 / Pressure問題 / ActionScore問題
- ➔ これらはすべて「コード調査候補」へ送る

### C. Replayでは**原理的に**答えが出ないこと ＜v2で新設＞

以下は、いくらリプレイを精読しても答えが出ない。
**すべて同じデッキで戦った試合しか手元に無いため。**

- **このデッキが他のデッキより強いか**
- 構築を変えたら何敗が減るか
- 事故率が構築由来かドロー運由来か

**これらは Replay監査ではなく、レーンD の A/B測定でしか判定できない。**
「証拠が出ていないから現状維持」という結論は、
**この方法では証拠が出せない**ことと区別すること。

### D. コード調査へ送る条件 ＜v1から1つ追加＞

以下をすべて満たすもののみ。

1. **再現性**: 複数のReplayで再現している
2. **影響度**: 勝敗へ直結している
3. **局所性**: 原因関数を狭く絞り込める
4. **作業量**: 最小変更で修正可能である
5. **上限見積**（v2追加）: STEP 5 の「勝率改善の上限見積」が他の候補より大きい

## §5. コード調査および修正前後監査

### 5-1. コード調査内容 ＜v1から変更なし＞

Policy経路 / ImmediateOutcome / ActionScore / `_result_key` / Tier / legacy / resource / pressure
をコードレベルで解析し、**ここで初めて原因を特定する**（Replayだけで決めつけない）。

### 5-2. 修正前監査（Pre-Fix Audit） ＜v2で3項目追加＞

修正に着手する前に、以下を記録する。

**v1から**: 今回のIssue / 影響関数 / 影響Replay / 既存テスト / 回帰リスク

**v2で追加（着手前に書くこと。測定後に書き足すのは禁止）**:

| 項目 | 内容 |
|---|---|
| **レーン** | A / B / C / D のどれか（§6） |
| **事前登録** | 対戦相手・N（戦数）・採用条件・kill条件を、**測る前に**書く |
| **タイムボックス** | この作業に使う上限時間。超えたら未完でも打ち切る |

### 5-3. 修正後監査（Post-Fix Audit：回帰チェック） ＜v1から変更なし＞

**目的以外の行動選択順位が変わっていないか**を確認する。

- **Replay比較**: 変更前の優先順位（1,2,3,4）と変更後の優先順位（1,2,3,4）を比較・記録
- **影響範囲**: 修正対象のAction（例: Attach）だけが変わったか。
  無関係なAction（Boss, Attack, Retreat, Development）まで波及していないか
- **想定外の順位変化**: 例「Attach修正によりBossの順位が変化」は新バグ候補として必ず記録

**維持すべき経路 / 変更されるべき経路を、事前に別々に列挙しておく**
（`ptcg_68_replay_research_audit.md` §3.10 のやり方が良い例）。

> **重要**: この工程は「壊していないこと」を確認するもので、
> **「強くなったこと」は確認できない**。採否は次の 5-4 で決める。

### 5-4. 実測ゲート（採否判定） ＜v2で新設・最重要＞

**5-3 を通っただけでは採用しない。ここを通って初めて採用する。**

#### 手順

**(1) 測る前に、事前登録を書く**

```
レーン        : B（最小修正）
変更内容      : Attach即時KO解禁の後続Attack到達価値をAttach候補へ伝播
対戦相手      : official_lucario / tomato_archaludon
N             : 各300戦（変更前・変更後で同じ）
採用条件      : 2相手の平均勝率が +8pt 以上
kill条件      : 平均が -3pt 以下、または CRASH>0、または conformance FAIL
タイムボックス: 2時間
```

**(2) 変更前（ベースライン）を測る**


#### N と、検出できる差の大きさ

**これは必ず理解しておくこと。** N が小さいと、偶然の揺れを改善と誤認する。

勝率50%付近で、**2条件の差**を判定する場合の目安（95%信頼区間）:

| N（各条件） | この幅より小さい差は「偶然と区別できない」 |
|---:|---:|
| 300 | **±約8pt** |
| 1,000 | ±約4.4pt |
| 2,000 | ±約3.1pt |

**つまり N=300 では、+8pt 未満の差を「改善した」と言ってはいけない。**

**残り時間を考えた現実的な方針（2026-07-29時点、Sim最終提出まで18日）**

- **+2〜3pt の細かい効果を追わない。** それを検出するには各条件 N=3,000 以上が必要で、
  時間が足りない
- **N=300 で明確に出る大きな効果（+8pt 以上）だけを採用する**
- 細かい効果の追求より、**STEP 0（ハード要件）と レーンD（デッキ）** を優先する。
  そちらの方が効果量が桁で大きい可能性が高い

まず所要時間を測ること。

```bash
time python3 ../../../../../verification/bench.py 300
```

これで N を増やせるかどうかを判断する。

#### 使ってはいけない測り方

| ✕ | 理由 |
|---|---|
| 族内ゲージ（`gauges/*`）で採否を決める | 相手を自分のパイロットが操縦するため勝率を +8〜+62pt 過大評価する |
| 対ランダムの勝率で採否を決める | ランダムは安全性の検査用。強さの指標にならない |
| 別々の提出のラダーレートを比較する | 相手分布・時刻・帯が違う。交絡する |
| 良い結果が出るまでNを増やす | 事前登録の意味が消える |
| 単一の相手だけで判定する | その相手固有の相性を拾ってしまう |

> **なぜ族内ゲージがダメか（実測）**: 相手デッキを自分のパイロットで操縦すると、
> 相手操縦者との実力差ぶんだけ勝率が上振れする。
> こちらの実測で steel相手 +62pt / 公式Lucario相手 +41pt の過大評価が出ている。
> **方向性の当たりをつける用途にだけ使い、採否には使わない。**

## §6. レーン分離と優先順位

### 6-1. 4つのレーン ＜v2で新設＞

**変更の種類によって必要なゲートが違う。同じ扱いにしない。**

| レーン | 内容 | 必要なゲート | 優先度 |
|---|---|---|---|
| **A. 安全性** | クラッシュ・不正手・デッキ返却・時間超過の修正 | STEP 0 のみ。**実測不要で即採用** | **最優先** |
| **B. 最小修正** | 局所的なPolicy修正。原則6が適用される | 5-3 回帰チェック ＋ 5-4 実測ゲート | 高 |
| **C. 構造変更** | 経路評価の導入など、設計に触る変更 | 5-3 ＋ 5-4 ＋ **維持経路の全数確認** ＋ 実行時間の再測定 | 中 |
| **D. デッキA/B** | 自陣デッキの構成変更 | 5-4 実測ゲートのみ（パイロットは固定） | **高** |

**レーンA は実測を待たない。** 落ちない・不正手を出さないことは効果ではなく前提条件なので、
勝率で正当化する必要がない。見つけ次第すぐ直す。

**レーンC は「最小修正」を名乗らない。** 例えば
「到達可能な後続Attack・damage・KO・Prize・Winまで経路として評価する」
（`ptcg_68_replay_research_audit.md` §3.9-4）は明確に構造変更であり、
`main.py` に +919行が入った v8 の実態とも一致する。
レーンCと宣言したうえで、重いゲートを課す。

### 6-2. レーンD：デッキA/B ＜v2で新設＞

**Replay監査では判定できない領域なので、独立したレーンとして必ず回す。**

パイロットを固定し、`--deck` で自陣デッキだけ差し替えて勝率を比較する。

```bash

  --opponent      ../../../../../verification/reference/official_lucario_agent.py \

# 候補デッキ（--deck で自陣だけ差し替え）
python3 ../../../../../verification/bench.py 300 --deck <候補デッキ.csv> \
  --opponent      ../../../../../verification/reference/official_lucario_agent.py \
  --opponent-deck ../../../../../verification/decks/official_lucario_2026-07-21.csv
```

**必ず守ること**

- 同名カードは**合計4枚以下**（基本エネルギーは除く）。
  **エンジンはこの制限を検査しない**（5枚でも通る）ので、人間が確認する
- ただしエンジンは**別種のデッキエラーは検査する**
  （`battle_start` の `start_data.errorPlayer >= 0` → 本番 `INVALID` = 即敗北）。
  「エンジンは何も見ない」と一般化しない
- デッキを差し替えたら **必ず `conformance.py` を再実行する**
  （`_read_deck()` が60枚でないと黙って旧デッキに落ちるため）

### 6-3. 優先順位の判定ロジック ＜v1から1要素追加＞

> Replay再現性 × 勝敗影響 × 原因確度 × 修正規模 × 回帰リスク × **勝率改善の上限見積**

最後の要素（STEP 5 で算出）が v2 の追加分。
**件数が多くても、勝敗反転の証明が少ない異常は優先度を下げる。**

## §8. 打ち切り基準 ＜v2で新設＞

### 8-1. 調査の打ち切り

- 各研究項目・各Issue調査に、**着手前に時間上限を宣言する**
- 上限に達したら結論が出ていなくても打ち切り、「不明」として記録して次へ進む
- **未着手の研究項目が多いことは問題ではない。**
  効果の大きい項目から着手し、締切までに間に合う範囲で止める

### 8-2. 実測の打ち切り

- 事前登録した N に達したら止める。**追加で測らない**
- kill条件に抵触したら即 revert する。「もう少し調整すれば」で粘らない
- 同じIssueに対する試行は**3回まで**。3回とも kill されたら、そのIssueは保留に回す

### 8-3. 締切からの逆算（2026-07-29 時点）

| 期日 | 内容 | 残り |
|---|---|---|
| 2026-08-09 | Simulation エントリー/合併 締切 | 11日 |
| **2026-08-16** | **Simulation 最終提出 締切** | **18日** |
| 2026-09-13 | Strategy 最終提出 締切 | 46日 |

**提出枠の制約（重要）**

- 提出は **1日5回まで**
- **最終順位は「直近2提出」のみで評価される**

つまり**最後に出した2つが、そのまま最終成績になる**。
弱いバージョンを最後に出すと、それまでの良い提出は評価対象から外れる。

→ **締切直前に未検証の変更を出さない。**
最終2枠は、実測で確認済みの最良版2つで埋める。

### 8-4. 残り18日の推奨配分

| 優先 | 作業 | レーン | 理由 |
|---|---|---|---|
| 1 | STEP 0 を通す（conformance / CRASH0 / check.py） | A | 上限を作っている可能性。実測不要で即直せる |
| 2 | `agent()` の最上位 try/except、`choose_indices` の空返し、`_read_deck` の ValueError | A | 同上。事故の芽を潰す |
| 3 | デッキA/B を最低1回 | D | 効果量が最大の未測定変数 |
| 4 | 上限見積が最大のIssueを1〜2件だけ | B | N=300 で +8pt 以上出るものに絞る |
| 5 | 構造変更（経路評価） | C | 時間が余った場合のみ。回帰リスクが大きい |
| – | 残りの研究項目（4〜11） | – | **締切内に終わらないなら着手しない。Strategyレポートの素材として温存** |

## §10. 最終目標

> STEP 0（安全性）→ Replay分析 → 異常分類 → 頻度集計 → **上限見積** → コード原因特定
> → レーン判定 → 実装 → 回帰チェック → **実測ゲート** → 採否決定 → 提出

このサイクルを、**打ち切り基準を守りながら**回し続け、
**勝率（レート）を向上させること**が最終目標である。

v1 との違いは2点だけ。

1. **安全性を先に確認する**（STEP 0）
2. **強くなったことを数字で確認してから採用する**（5-4）

方法論そのものは v1 のまま。**測って決める工程を足しただけ。**
