# Playbook — セッション運用テンプレート (2026-07-20制定)

どのモデル(Opus等)がこのリポジトリで作業しても、2026-07-19〜20セッションと同じ
働き方を再現するための運用規範。**CLAUDE.mdから参照される。開発方針の議論を
始める前に必ずこれを読む。**

## 0. セッション開始チェックリスト

1. メモリ(MEMORY.md)と decisions.md の末尾2-3件を読む
2. 走行中の背面ジョブ・未完タスクの有無を確認
3. Kaggle提出枠の現状(直近2提出=最終順位)を確認してから提出に触れる
4. 目的関数を思い出す: **賞金はStrategy部門(Model70%/Deck20%/Report10%)。
   競争相手は5,068エージェントではなく197本のwriteup。LB順位は配点の約14%。**
5. **監査トリガー(§7)の発火状態を点検する**(週次T5の期限、未検証のT1予測、
   直近の合格に対するT4懐疑パスの未消化がないか)

## 1. バイアス対策の型(このプロジェクト最大の教訓)

作業が進むほど仮説に愛着が生まれ、選択肢が狭まる。以下を**機械的に**適用する:

- **対照実験を先に**: 新実装Xを測る前に「Xを全部オフにした構成が既存版と50%になる」
  ことを確認する(リファクタ無罪の証明)。これを飛ばして得た差分は全て疑わしい。
- **族外較正は「1点取る」ではなく採否判定の主指標にする**(2026-07-21 D27で格上げ)。
  自前パイロットが相手デッキを操縦するゲージは**スクリーニング専用**とし、絶対値を語らない。
  **族内ベンチの誤差は「実際の相手操縦者と我々の操縦者の実力差」に比例する**
  (実測: steel相手+62pt / 公式Lucario相手+41pt / りょーちんagent相手+8pt)。
  自分より上手い相手が増える帯に上がるほど、族内ベンチは無意味になる。
  利用可能な族外ゲージ(すべて `verification/reference/`、**検証専用・提出禁止**):
  - `steel_agent.py` + `decks/steel_archaludon.csv` (Archaludon、公開820点帯)
  - `official_lucario_agent.py` + `decks/official_lucario_2026-07-21.csv`
    (**ホスト公式サンプル。実ラダーの相手と60/60枚一致=実環境の再現**)
  - `official_abomasnow_agent.py` + `decks/official_abomasnow_2026-07-21.csv`
  - チームメイトのagent(`decks/mega-starmie-ex-deck/main.py`)も族外操縦者として使える
  他アーキタイプの公式サンプルはKaggle Codeタブ(著者kiyotah)から同様に取り込める。
- **事前登録**: 仮説・N・合格閾値を測定前にdocs/memoに書く。
  N=200のSEは約3.5pt → **3pt差の結論をN=200で語らない**。効果量5ptの検出はN≈800。
  8対面の符号一致(方向性)は少数Nでも堅い証拠として扱ってよい。
- **判定は「較正済み遭遇加重合成指標(CEW)」1本で行う**(2026-07-21 D29で改訂)。
  複数の非退行ゲートを独立に課してはいけない: **4条件だと真に効果ゼロの変更でも
  65.1%の確率でどれかが「退行」と誤検出され、良い変更を系統的に捨てる**。
  退行は合成指標に遭遇率の重みで自動反映される。
  現行のCEW = Lucario(公式agent) 53.8% + Archaludon(steel) 38.6% + Abomasnow(公式agent) 7.6%、
  基準線34.5%。**N=800/セル・閾値+2pt**(真の+5ptの採用率96.4%、1実験2,400戦≒36分)。
  別建てで残すのは効果量ではなく**正当性の検査**のみ: CRASH=0 / vs random ≥96% / check.py。
- **標的選定はデッキ側を優先する**: 実測の効果量はデッキ介入 平均+7.7pt に対し
  パイロット介入 平均+0.1pt(2026-07-21時点、n=2/n=6)。パイロット微調整に時間を
  集中させない。
- **kill基準とタイムボックスを着手前に決める**(サンクコスト遮断)。
  実例: iter4は「7/24害分析・8/2 Stage2・総投下12h」で事前固定(D19)。
- **反証テスト**: 結論を書く前に「この結論が間違いなら何が観測されるはずか」を
  1つ挙げて実際に確認する。
- **専門家評議会**: 大きな方針決定・行き詰まり・数回の反復で改善しない時は
  `/council` (`.claude/skills/council/`) を起動(発火条件の定量形は§7)。4役(戦略/赤チーム/ドメイン/実装)の
  サブエージェントに**一次資料を直接読ませ**、既存決定への遠慮を明示的に禁じて
  独立見解を取る。要約を渡さない(要約は自分のバイアスを運ぶ)。

## 2. 測定規律

- **CPU直列**: 時間予算制エージェントのベンチは並列禁止(D16)。長時間ジョブは
  `caffeinate -dims`でスリープ抑止し背面実行、完了通知で回収。
- **vs randomは必須ゲート**(パッシブ相手検査。攻撃的ゲージは自滅バグを隠す — D15)。
- **効果量の判定は §1 の較正済み合成指標(CEW)1本で行う**(D29改訂)。
  自前パイロットが相手を操縦する族内ゲージ(Alakazam/Grimmsnarl型・自パイロット操縦Lucario)は
  相手実力差に比例して+8〜+62pt過大評価するため、**採否の主指標にしない**
  (スクリーニング用途に限る)。**独立に残す検査は効果量ではなく正当性のみ**:
  CRASH=0 / vs random ≥96% / check.py。donk_meterやゲージ勝率を独立ゲートとして課さない
  (D29: 独立4条件で真に効果ゼロでも65.1%が誤検出。この規則は帯の実遭遇分布に紐づく——
  帯が変われば重みとゲージを再計算する)。
- デッキA/Bの最良形式: 「変種 vs 現行デッキ・同一パイロット両側」の直接対決
  (150戦〜)。deck×pilot非分離(D9)のため、デッキ単体の議論をしない。
- 判断ログ(V3_LOG形式)で上書き/判断の露出を記録し、勝敗と突合できる形にする。
  ただし試合単位の相関は状態交絡があるので、因果はクラス単位ON/OFF A/Bで取る。
- **帯構造(実遭遇分布)が変わったら、走行中の実験の合格基準(プール重み)を再計算して
  から続行する**(2026-07-20評議会: Stage2の64%加重基準はmid/low帯の遺物のまま
  700+帯に昇格し、消滅した対面への最適化に6hを浪費しかけた)。
- **週次で実ラダー遭遇分布を再検死する(常設タスク)**: replay_analysisで直近提出の
  全戦(勝敗両方、生存バイアスを避ける)を取得しアーキタイプ分類。損失寄与=遭遇率×負け率
  で優先対面を決め直す。2026-07-21の例: 負け13戦のみの初回検死はLucarioを最多敗因と
  誤認したが、N=60全戦(勝敗込み)ではArchaludonが勝率20%で損失寄与最大と判明した
  (data.md参照)。**勝ち試合を除外した検死は生存バイアスを持つ**。

## 3. 実装規律

- agent()は絶対に落ちない・違法手を返さない。変更後は`@robustness-guard`。
- **ctypes境界はNULLガード必須**(`_engine_json`パターン)。`string_at(None)`は
  try/except不能のセグフォルト=対局没収(2026-07-20に提出版で発見・修正済み)。
- env設定の`int()`はimport時に落ちない`_env_int`型で。
- 新機構は必ずフラグでオフ可能にし、アブレーション可能な形で実装する。
- 探索系の教訓: **強い保守構造(対標本差分+マージン上書き)の上に汎用探索を
  足すと壊れる**(D18-19の機構診断)。評価関数を信用しない層(終局検知)→
  クラス限定の順で露出を増やす。

## 4. 提出規律

- 手順: フルゲート → `check.py`(deck60枚/同名4枚/stdlib/tar構造/スモーク20戦) →
  **ユーザー承認** → 提出 → decisions.mdにDn記録。
- 最終ランキングは直近2提出。較正目的の提出は「後で上書きすればコストゼロ」だが
  枠(5/日)とレーティング表示の一時低下を伴う。
- 8/13以降は凍結・最終2枠=同一ベスト×2(D19提案、チーム合意待ち)。

## 5. 記録規律

- 意思決定 → `decisions.md`(Dn形式: 経緯/決定/根拠/状態)
- 実測データ → `data.md`(日付節、数字はCI付き)
- 大きな方針転換・評議会 → 独立ファイル(例: plan-2026-07-20-council.md)
- セッションの終わりに自分のメモリ(MEMORY.md系)を更新
- **誤りが判明したら元の記録を上書きせず「訂正」として追記**(例: Rock Inn=
  スタジアムではなくCrustleの特性、の訂正)

## 6. 自律運転のコツ(Fableセッションの再現)

- 長時間測定は背面+通知で回し、待ち時間に次の準備(スクリプト・変種構築)を進める
- 定期監視が要る時は/loopまたはcron、外部イベント待ちはMonitor
- ユーザー承認が要るもの(提出・デッキ転換・チーム合意事項)は明確にリスト化して
  提示し、それ以外は止まらず進める
- 報告は「結論先出し・表・次の一手」。中間発見も必ず最終メッセージに含める

## 7. 監査トリガー (2026-07-22制定 = D32。外部レビュー原案を改訂して採用)

監査(赤チーム視点への切替)は**裁量ではなくトリガーで発火させる**。
根拠: D29の自己批判はユーザーの促しがなければ起きず、7件連続棄却(EXP4〜6b)の間に
自発的な監査はゼロだった。「行き詰まったら/council」(§1)は発火条件として曖昧すぎた。

| # | トリガー(定量) | 発火時の行動 |
|---|---|---|
| **T1 予測外れ** | 提出ごとに事前登録したラダー予測が、N≥60全戦検死でCI外 | 較正監査(重み・ゲージ・較正法則の再点検) |
| **T2 連続棄却** | 同一系統の事前登録実験が3連続棄却 | 系統打ち切り+標的選定の監査 |
| **T3 分布移動** | 週次検死(§2)で遭遇分布が現行CEW重みの多項95%CI外 | 重み再計算(**義務・承認不要**・結果は報告) |
| **T4 合格** | 介入が判定規則を「合格」した | 自動懐疑パス: ベイズ検査+独立追試+次回提出へのラダー予測の事前登録(D31手続きの恒久化。**勝者の呪いは成功時に来る**=D26) |
| **T5 外部摂取** | 週1: 公開notebook/discussion走査+直近提出の全戦検死。新規外部agent/リストの出現 | 新ゲージ化を検討(D27=公式サンプル発見の再現を仕組み化。**内向き防止の本丸は自己懐疑ではなく外部証拠の摂取**) |
| **T6 執筆整合** | (執筆フェーズ)主張台帳にない数値・N/CIなしの数値・族内測定由来の数値を成果物に書いた | 停止してdata.mdと突合(fig_deck_matrix自己矛盾=D30の再発防止) |

- **発火時の深さは2段階**: ①軽い自己監査(赤チーム形式で上位ボトルネック+反証実験を提示)
  → ②所見が構造的(計器・デッキ・判定規則に及ぶ)なら`/council`へ昇格。
- **T1のセンサーは提出時の義務**: 提出前に「対面別勝率・CEW由来の総合予測」を
  data.mdに事前登録する。予測なしの提出はT1を無効化するので原則行わない。
- **閉じた決定の再審は、閉鎖時に存在しなかった新証拠がある場合のみ**(ゾンビ防止。
  v3/iter4は対照実験+機構解明つきで棄却済み=新証拠なしに復活させない。
  正当な再審の型はEXP5/D27:「較正ゲージは棄却判定の時点で存在しなかった」)。
- **判定規則(閾値・指標の定義)の変更はD29の手続き経由のみ**: 検定力計算+事前登録+
  ユーザー承認。行き詰まりや不満を動機に指標を書き換えない(ゴールポスト移動の構造的防止)。
  ※T3の**重み再計算はこれに該当しない**(計器の定期較正であり義務)。
- **ユーザー承認必須は4つ**: 提出実行 / デッキ転換 / 判定規則の変更 / チーム合意事項。
  それ以外(重み再計算・測定・実装・記録)は止まらず進めて報告する(§6)。
- **フェーズで既定モードが変わる**: 〜7/26=実験(事前登録+kill基準)。以降8/13まで=
  穴D・図表・提出規律、8/17以降=執筆。実験フェーズ終了後の「探索」はコード変更ではなく
  主張台帳・図表・外部偵察(T5)を指す。実験の追加はT1〜T5の発火を根拠に持つ場合のみ。
