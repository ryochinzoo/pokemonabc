# Playbook — セッション運用テンプレート (2026-07-20制定)

どのモデル(Opus等)がこのリポジトリで作業しても、2026-07-19〜20セッションと同じ
働き方を再現するための運用規範。**CLAUDE.mdから参照される。開発方針の議論を
始める前に必ずこれを読む。**

## 0. セッション開始チェックリスト

1. メモリ(MEMORY.md)と decisions.md の末尾2-3件を読む
2. 走行中の背面ジョブ・未完タスクの有無を確認
3. Kaggle提出枠の現状(直近2提出=最終順位)を確認してから提出に触れる
4. 目的関数を思い出す: **賞金はStrategy部門(Model70%/Deck20%/Report10%)。
   競争相手は5,068エージェントではなく197本のwriteup。LB順位は配点の約14%。**

## 1. バイアス対策の型(このプロジェクト最大の教訓)

作業が進むほど仮説に愛着が生まれ、選択肢が狭まる。以下を**機械的に**適用する:

- **対照実験を先に**: 新実装Xを測る前に「Xを全部オフにした構成が既存版と50%になる」
  ことを確認する(リファクタ無罪の証明)。これを飛ばして得た差分は全て疑わしい。
- **族外較正**: 結論を出す前に、自前ファミリー外の物差しで1点測る
  (steel: `verification/reference/steel_agent.py` + `decks/steel_archaludon.csv`)。
  実例: 族内で一貫していた「v3劣後」が族外で消失した(data.md 2026-07-20)。
  **自前パイロット同士のベンチは「自分の方針分布への適応度」しか測れない。**
- **事前登録**: 仮説・N・合格閾値を測定前にdocs/memoに書く。
  N=200のSEは約3.5pt → **3pt差の結論をN=200で語らない**。効果量5ptの検出はN≈800。
  8対面の符号一致(方向性)は少数Nでも堅い証拠として扱ってよい。
- **kill基準とタイムボックスを着手前に決める**(サンクコスト遮断)。
  実例: iter4は「7/24害分析・8/2 Stage2・総投下12h」で事前固定(D19)。
- **反証テスト**: 結論を書く前に「この結論が間違いなら何が観測されるはずか」を
  1つ挙げて実際に確認する。
- **専門家評議会**: 大きな方針決定・行き詰まり・数回の反復で改善しない時は
  `/council` (`.claude/skills/council/`) を起動。4役(戦略/赤チーム/ドメイン/実装)の
  サブエージェントに**一次資料を直接読ませ**、既存決定への遠慮を明示的に禁じて
  独立見解を取る。要約を渡さない(要約は自分のバイアスを運ぶ)。

## 2. 測定規律

- **CPU直列**: 時間予算制エージェントのベンチは並列禁止(D16)。長時間ジョブは
  `caffeinate -dims`でスリープ抑止し背面実行、完了通知で回収。
- **vs randomは必須ゲート**(パッシブ相手検査。攻撃的ゲージは自滅バグを隠す — D15)。
- 標準ゲート: vs random 300 + Alakazam/Grimmsnarlゲージ + Lucario実ラダー +
  donk_meter + **steel族外** + CRASH=0。
- デッキA/Bの最良形式: 「変種 vs 現行デッキ・同一パイロット両側」の直接対決
  (150戦〜)。deck×pilot非分離(D9)のため、デッキ単体の議論をしない。
- 判断ログ(V3_LOG形式)で上書き/判断の露出を記録し、勝敗と突合できる形にする。
  ただし試合単位の相関は状態交絡があるので、因果はクラス単位ON/OFF A/Bで取る。

## 3. 実装規律

- agent()は絶対に落ちない・違法手を返さない。変更後は`@robustness-guard`。
- **ctypes境界はNULLガード必須**(`_engine_json`パターン)。`string_at(None)`は
  try/except不能のセグフォルト=対局没収(2026-07-20に提出版で発見・修正済み)。
- env設定の`int()`はimport時に落ちない`_env_int`型で。
- 新機構は必ずフラグでオフ可能にし、アブレーション可能な形で実装する。
- 探索系の教訓: **強い保守構造(対標本差分+マージン上書き)の上に汎用探索を
  足すと壊れる**(D18-19の機構診断)。評価関数を信用しない層(終局検知)→
  クラス限定の順で露出を増やす。

## 4. 提出規律

- 手順: フルゲート → `check.py`(deck60枚/同名4枚/stdlib/tar構造/スモーク20戦) →
  **ユーザー承認** → 提出 → decisions.mdにDn記録。
- 最終ランキングは直近2提出。較正目的の提出は「後で上書きすればコストゼロ」だが
  枠(5/日)とレーティング表示の一時低下を伴う。
- 8/13以降は凍結・最終2枠=同一ベスト×2(D19提案、チーム合意待ち)。

## 5. 記録規律

- 意思決定 → `decisions.md`(Dn形式: 経緯/決定/根拠/状態)
- 実測データ → `data.md`(日付節、数字はCI付き)
- 大きな方針転換・評議会 → 独立ファイル(例: plan-2026-07-20-council.md)
- セッションの終わりに自分のメモリ(MEMORY.md系)を更新
- **誤りが判明したら元の記録を上書きせず「訂正」として追記**(例: Rock Inn=
  スタジアムではなくCrustleの特性、の訂正)

## 6. 自律運転のコツ(Fableセッションの再現)

- 長時間測定は背面+通知で回し、待ち時間に次の準備(スクリプト・変種構築)を進める
- 定期監視が要る時は/loopまたはcron、外部イベント待ちはMonitor
- ユーザー承認が要るもの(提出・デッキ転換・チーム合意事項)は明確にリスト化して
  提示し、それ以外は止まらず進める
- 報告は「結論先出し・表・次の一手」。中間発見も必ず最終メッセージに含める
