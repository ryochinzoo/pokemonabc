一番大事な発見5つ(カード知識と掛け算してほしい)

① ラダーの相手の正体は「公開コードのコピー」だった

実対戦ログから相手の60枚を抽出して照合した結果: ルカリオ=主催者の公開サンプルと60枚完全一致(コピーされた回数997回)。ブリジュラス=公開ノート「TOMATOMATO」のリストと完全一致。ドラパルトも主催者サンプル。つまり敵の中身がgithubに置いてあるようなもので、これを手元に連れてきて練習相手にしている(verification/reference/)。

② 族内測定の罠(このプロジェクト最大の教訓)

「相手のデッキを自分のAIに持たせて測る」と、相手が本来の専用ロジックで動かないので勝率が甘く出る。実測でのズレ: ブリジュラス相手+62pt、ルカリオ相手+41pt、りょーちんのagent相手+8pt。ズレの大きさは相手パイロットとの実力差に比例する。だから採否の判定は必ず「本物の敵」(族外ゲージ)で測る。

③ 人間の定石はAIパイロットに移植できない(実測3連発)

人間の定石実測結果
ヨノワールのダメカン砲コンボ(人間メタの定番)AIは一度も決められず死に荷物。抜いたら直接対決64.7%勝ち
エースバーンのエネ加速(勝ち組リスト6/6が採用)うちのAIでは発動0.12回/試合の死に札
「マリガン率60%は異常、たねを増やせ」増やすほど単調に悪化。調べたらエンジンはマリガンのペナルティを実装していない

りょーちんのカード知識は最強の武器だけど、「人間の対戦で正しい」と「このエンジンでこのAIで正しい」は別物 ─ というのがうちの一番の学び。知識で仮説を出す→計器で数値にする、の分業が理想。

④ デッキとパイロットは切り離せない(昨日の王座防衛戦)

ガルーラ型とフーディン型は、較正済み計器のスコアでは現デッキを+14〜16点も上回った。ところがランダムに手を選ぶだけのAI相手の勝率が84〜90%に落ちる(まともな構成なら96%以上出る)。つまりうちのパイロットはその2つのデッキだと自滅する。デッキ単体の強さは存在せず、「マシン×ドライバー」のセットでしか評価できない。りょーちんの専用ロジック×りょーちんのリストにも同じことが言える ─ だから他人の物差しではなく、本物の敵ゲージで自分のセットを測るのが唯一フェアな比較になる。

リポジトリの地図 ─ どこに何があるか

src/input/datasets/decks/<デッキ名>/
デッキ実験の単位。main.py(パイロット)+deck.csv(60枚)+cg/(エンジン)。starmie-aggro/ がいまのライブ版。エンジンのバイナリ(libcg.dylib等)はgitに入れてないので、無ければKaggleのsample_submissionからコピー。
verification/
測定道具箱(下のレシピ集で使う全部が入っている)。bench.py=勝率測定、cew.py=総合点計算機、donk_meter.py=序盤事故率、selfplay.py=対戦ハーネス本体。
verification/reference/
本物の敵たち。official_lucario / tomato_archaludon / official_dragapult / official_abomasnow / steel の5体。すべて公開コードの取り込みで、検証専用・提出物に混ぜるのは厳禁(Strategy部門は独自性を審査されるため)。
verification/decks/
ゲージ用・実験用のデッキリスト置き場(実ラダーから抽出した本物のリスト多数)。
replay_analysis/
Kaggleの実対戦ログ(リプレイ)を落として解剖する道具。t1_verdict.py=対面別成績の集計、mechanism_autopsy.py=負け方の中身(どのワザを何回撃ったか等)、trace_replay.py=1試合を人間が読める形で再生。
docs/memo/
頭脳の外部記憶。playbook.md=チームの行動規範(測定の作法)、decisions.md=意思決定ログD1〜D35(「なぜそうしたか」が全部ここ)、data.md=実測データ全部、claims-ledger.md=レポートに書く主張の証拠グレード台帳、figures/=レポート用の図。
.claude/skills/submission-check/scripts/check.py
提出前の最終検査(60枚・同名4枚・import違反・tar構造・20戦スモーク)。

りょーちんのagentを読んだ上での提言

まず前提: main.py 3,383行、BoardState / MasterEvaluator / ActionFactory / SelectionResolver / DamageCounterEngine ときれいに層が分かれていて、ムンキドリのダメカン移動をシリアル番号でロックする専用ロジックまである。構造はうちのより整理されてるくらいで、方向性は全く正しい。その上で、実測ベースの提言が3つ。

提言1(最優先・Codexで30分): 「没収負け」の穴を2つ塞ぐ

このコンペはプログラムが例外で落ちる or ルール違反の答えを返すと、その場で没収負け。いまの agent() には確率は低いが致命傷になる穴が2つある:

  • 全体を守るtry/exceptが無い。3,383行のどこか1行が想定外の盤面で例外を出したら即没収。実際うちも提出済みコードにセグフォ級の穴を後から見つけて修正した経験がある。
  • return [] になる経路が複数ある(actionsが空の時など)。エンジンが「最低1つ選べ」(minCount=1)と言っている局面で空リストを返すと違法手=没収。長い対戦では必ずいつか踏む。

→ 直し方は「agent()を安全な外装で包む」だけで、既存ロジックは一切変えない。プロンプトP1をCodexに貼れば終わる。

提言2: 自分の「本当の位置」を本物の敵で測る

りょーちんのセット(専用ロジック×自リスト)の較正済みスコアはまだ誰も測っていない。参考値としてあるのは「りょーちんのリストをうちのパイロットに持たせた場合=27.6」だけで、これは専用ロジックの価値をゼロカウントした不当に低い数字。ムンキドリ運用などはうちのAIには真似できないので、本人のagentで測れば確実にもっと上に出る。R1→R2→R3の順に流せば40分で自分の現在地とマッチアップ別の弱点が数字になる(プロンプトP2で自動化できる)。そこからの改善議論なら、カード知識×計器で本当に噛み合う。

提言3(ディスカッションしたいアイデア): 壁の急増とRisky Ruins

壁デッキ(イワパレス系)が3%→15%に急増している。りょーちんのデッキにはRisky Ruins 4とBoss's Orders 3が入っていて、ここはこちらより対応力の設計思想がある部分のはず。「対壁・対ブリジュラスにカード知識で何ができるか」の仮説をりょーちんが出し、こっちの較正ゲージで数値化する ─ という分業を今日のMTGで試したい。1仮説あたり測定コストは30分程度。

1つだけ注意(測定の作法) 改善を測る時は「何を測って、何点以上なら採用か」を測る前に決めて書き残す(事前登録)。あとN=200程度の300戦未満で2〜3ポイント差を信じない(誤差幅の方が大きい)。うちは10回の実験で9回「効果なし」を正しく見抜けたが、それはこの作法のおかげ。逆にこれを守れば、失敗した実験すらレポートの得点素材になる。

P1. agent()を「絶対に落ちない・違法手を返さない」ようにする(最優先)
あなたはPythonのシニアエンジニアです。ポケモンカードの対戦AIコンペのエージェントを
堅牢化してください。対象は src/input/datasets/decks/mega-starmie-ex-deck/main.py です。

## 背景(コンペの契約)
エンジンは agent(obs) を呼び、以下の契約に違反すると即座に没収負けになります:
- obs.select が None のとき: 60枚のデッキ(カードIDのリスト)を返す
- それ以外: 整数インデックスのリストを返す。条件は
  (a) obs.select.minCount <= len(結果) <= obs.select.maxCount
  (b) 各インデックスは 0 以上 len(obs.select.option) 未満
  (c) 重複なし
- どんな入力でも例外を外に漏らしてはいけない(例外=没収)

## 現状の問題
1. agent() の中身を守る包括的な try/except がなく、内部ロジックの例外がそのまま漏れる
2. 「actionsが空」等の経路で return [] するが、minCount>=1 の局面では [] は契約違反

## やること
1. 既存の agent() を _agent_impl() にリネームする(中身は1文字も変えない)
2. 新しい agent() を作る:
   - _agent_impl() を try/except で呼ぶ
   - 返り値を契約(a)(b)(c)で検証し、違反していれば安全なフォールバックに差し替える
   - 例外時・検証失敗時のフォールバック: minCount が k なら list(range(k))
     (k=0 なら [])。obs.select が None なら DECK を返す
   - obs が dict の場合の変換は既存どおり維持する
3. フォールバックが発動したら print で1行ログを出す(デバッグ用、標準出力でよい)

## やらないこと
- _agent_impl 内部のロジック変更・リファクタリング・整形は一切しない
- 新しいライブラリの追加はしない(標準ライブラリのみ)

プロンプトのコツ(3つだけ)

上のプロンプトが長いのには理由がある。AIへの依頼は「目的・制約・確認方法」の3点セットにすると精度が桁で変わる:

  1. 目的と背景を先に書く(「なぜ」を知らないAIは平気で本末転倒なことをする)。特に「やらないこと」を明記すると暴走が止まる。
  2. 受け入れ基準=実行して確認できるコマンドを必ず入れる。「動くようにして」ではなく「このコマンドがPASSするようにして」。
  3. エラーが出たら全文貼る。要約せず、ターミナルの出力をそのまま。

この型さえ守れば、P1〜P4みたいなプロンプトは自分でいくらでも量産できる。
