基盤の構成と昨夜の2提出 — 根本から理解する

2026-07-29 作成 / 対象: 55058443・55060473 の中身と理由、システム全体の設計思想、いま何をやろうとしているか

先に結論だけ3行
  1. 昨夜の2提出は まったく同じパイロット(main.py、バイト単位で同一)に、違うデッキを載せたものです。
  2. 理由は順位取りではなく計測 — 「操縦者を固定してデッキだけ変える」ことでしか測れない量があるからです。
  3. いま我々がやっているのは「強いAIを作る」より前段の「強さを正しく測れる装置を作る」で、それが勝負どころです。

2. ロジックは同じか、別か

ロジック(パイロット=main.py)は完全に同一です。「同じくらい似ている」ではなく、SHA256ハッシュがビット単位で一致しています。

両方の main.py: 50863cfa97d91f7d5e187a3111984d0a8e996577723c2657e332a43eada4cf35

deck.csv だけが違う:
  starmie-aggro   : d8ef04fa2c65ae9f98f180d2ba80c295c1b9501d63a1c95fb4c9d2e1c3eb2e40
  dragapult-calib : 4868ecced4f58da29d0c3971a62e552b069fc9d6e6bc3d69c4a7cebcb2747710

これはこの大会の基本構造から来ています。提出物は必ず デッキ(60枚) × パイロット(main.py) のペアです。そして我々のパイロットは特定デッキ専用に書かれた台本ではなく、渡された盤面を汎用的に評価して指し手を選ぶエンジンなので、別のデッキを載せてもそのまま動きます。

なぜ「わざと」同じロジックにしたのか — これが実験の核心です。
2つの変数(デッキ・パイロット)のうちパイロットを固定してデッキだけ動かすと、観測された差はデッキ由来だと言い切れます。逆に「デッキを固定してパイロットだけ動かす」と、差はパイロット由来。この2種類の対照実験を積み重ねることでしか、後述する「較正の法則」は測れません。

3. なぜ出したのか — 順位ではなく計測が目的

両方とも提出メッセージに「Purpose is measurement, not ranking」と明記しています。目的はそれぞれ違います。

① 55058443(王者) — 「重みの前向き検証」

我々は勝率を測るとき、実ラダーでどの相手にどれくらい当たるかで重み付けした合成指標(CEW)を使っています。7/26にその重みを更新しました(Dragapult枠が 9.8% → 15.5% など)。

ただしその更新は過去データを見て後から直したもの(後ろ向き)。「新しい重みが本当に正しいか」はまだ一度も前向きに試していなかった。
→ そこで提出前に「新重みだとラダー成績はこうなるはず」という数値(H1 = 44.39%)を書いて封をしてから提出しました。今夜の検死でそれが当たっているかを見ます。

② 55060473(dragapult-calib) — 「較正法則の3つ目のデッキ」

後述の「較正の法則」は、これまで2種類のデッキでしか検証していませんでした。3種類目として、①とまったく毛色の違うデッキ(2進化コントロール)で同じ法則が成り立つかを見ます。法則が特定デッキの偶然でないことを示すためです。

提出枠を使うコストはほぼゼロ、という事実

最終順位に効くのは凍結時点の直近2提出だけで、それまでは何を出しても後から上書きできます。しかも1日5枠が毎日戻ってくる。だから「較正データを取るために出す」のは実質タダです。(公式Sim最終提出は8/16。締切後も〜8/31頃までラダーは回り続けて収束後にLB確定)

第2層: パイロット(main.py)の中身

約3,900行。3段構えです。

段役割実測された価値
①貪欲層(v1)盤面を手書きの評価関数で採点し、いちばん点の高い手を選ぶ。ダメージ・エネ・サイド枚数などを重み付け土台(単体評価なし)
②探索・上書き層本物のエンジンを使って先読み(決定化 ×2 → ロールアウト)。貪欲層の選択と食い違い、その差が閾値を超えたら上書きする+13.62pt
CI[+11.40,+15.84]、12.0σ
(各腕3,200戦の対照実験)
③安全網例外・不正手・時間超過を絶対に外に出さない。agent()は必ず合法な選択を返す実ラダーCRASH=0
②の中にある既知の欠陥(今夜これを直す)

先読みするには「相手の見えない山札」を仮定する必要があります。そのために _META_DECKS という相手デッキ辞書を持っていて、見えたカードから「相手はこの型だろう」と当てて60枚を復元します。
ところが辞書の中身は 2026-07-14 時点のラダー実測5デッキのままで、今いちばん当たる Lucario / Archaludon / Dragapult / Abomasnow が1つも入っていません。つまり計器で重み100%を占める4対面すべてで、先読みは相手の山を「ほぼ草エネルギーの束」と誤って仮定して計算しています。

第3層: 較正済み計器(ここが我々の独自性)

出発点になった発見(2026-07-21): 自己対戦で相手デッキを自分のパイロットで動かして測ると、勝率が+8〜+62pt も過大に出る。しかもそのズレはランダムではなく「本物の操縦者と自分の腕の差」に比例していた。

→ だから相手側は本物の他人のAIに操縦させる(=族外ゲージ)。使っているのは公式サンプルAgent 3種+公開notebook 1種で、公式Lucarioは実ラダーの相手と60枚中60枚一致していました(=ラダーそのものをローカルに再現できた)。

45.1%Lucario(公式サンプル)
33.8%Archaludon(tomato系)
15.5%Dragapult(公式)
5.6%Abomasnow(公式)

この4つの勝率を上の重みで合成した1つの数字が CEW。基準線 43.13%、採用閾値 +2.0pt。測定は Neyman配分 N=3,200(1562/1040/426/172)。
限界も開示しています: 実ラダー遭遇の33.3%しかカバーできていない(遭遇1位のAlakazam 20%にはゲージが無い)。

第4層: 規律(なぜ必要か)

我々は10件以上の改良案を試して、採用できたのは2件だけです。棄却が多いのは能力の問題ではなく、先に「これを超えなければ捨てる」と数字で宣言してから測っているからです。この規律がないと、出た結果を見てから基準を動かしてしまう(=自分を騙す)。

仕組み中身
事前登録測る前に N・閾値・kill条件・予測を文書に書いて凍結する
T1〜T7トリガー監査を「気が向いたら」でなく機械的に発火させる。T1=提出ごとのラダー予測検証、T3=遭遇分布が動いたら重み再計算(義務)、T7=設計レビュー
T7パネル4つの視点(統計/ドメイン/実装/前提)のサブエージェントに独立に叩かせ、別モデルで検証してから編集長が裁定。昨夜も24件の指摘が出て6件が必須修正になりました
主張台帳レポートに書く数値は全てここを経由。「確証/弱確証/探索的/撤回」のラベル必須

5. いまの方針 — なぜ「記事を先に書く」のか

Strategy部門の配点: Model 70% + Deck 20% + Report 10%。そして Model 70% の内訳は5項目(説明/独自性/安定性/頑健性/Sim成績)。
つまりラダー順位は総配点の約14%しかなく、残り86%は「書かれたもの」でしか審査されない。公式も「LB中下位でも高得点可能」と明言しています。

そこで7/28に方針を「逆算」に切り替えました。記事を先に全文書き切って、どこで論証が詰まるかを計器として使う。8月下旬に書き始めると、そこで見つかった穴を埋める測定窓(8/8で実験終了)が既に閉じているからです。

実際にやってみた結果(これが今回いちばんの収穫)

全文1,970語を書き切ってギャップが8件出ました。そして新規実験を要する穴は1件もありませんでした。
最大の穴は「で、結局強くなったのか?への答えが弱い」。しかしこれは証拠不足ではなく構成の失敗でした — 我々の最大の測定値 +13.62pt が「探索層の話」として脇に置かれていて、「エージェントの正味の強さ」として提示されていなかった。再配置だけで解決しました。
