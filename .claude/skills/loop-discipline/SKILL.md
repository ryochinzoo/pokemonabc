# loop-discipline — 前進の既定値

> 起草 2026-07-31(ゆうじ指示)。外部セッション由来の旧版はディスクに到達しておらず、
> 本版は decisions.md / claims-ledger.md / 2026-07-31セッションの実測に照合して新規起草。
> 出典記事の要約は reference.md、実例の詳細は background.md。

## 原則: 凍結されるのは実装であって、測定ではない

- **実装の凍結(維持・保守的でよい)**: `main.py`・デッキ・提出物の変更は、
  事前登録+T7+ゲート(vs random / CRASH / check.py / conformance / robustness-guard)を通す。
  凍結カレンダー(D55: 穴D 8/3、実験終了 8/8、凍結 8/13)に従う。
- **測定/調査の凍結(不要・禁止)**: 対戦ゼロ・CPUゼロ・`main.py` 不変の作業
  (リプレイ解析・エンジンソース照合・記録の突合・仕様確認)に凍結は適用されない。
  これを凍結扱いすることを禁止する。

## 前進の既定値

1. **対戦ゼロ・`main.py` 不変の作業は、許可を求めずに走らせる。**
   完了後に結果と一次ログ(ディスク保存必須、台帳#29教訓)で報告する。
2. **測定の依頼に、スケジュールの懸念で答えてはならない。**
   「締切が近い」「凍結前だから」「穴Dがあるから」は測定を止める理由にならない
   (D55の予約は8/3のCPUであり、それ以外の日の対戦ゼロ作業と競合しない)。
3. **「新しい主張を足す測定」と「既存主張のラベルを上げる測定」を区別する。**
   後者は語数予算で詰まらない(語数中立かマイナス)。語数の希少性は前者にだけ効く。
   語数は空間的に希少だが時間的には希少でない。8/13までの時間だけが時間的に希少。
4. **後回しの理由には実測/推定タグを付ける。** 推定タグの理由は、後回しにする前に
   その推定自体を検証する(検証コストは通常、後回しのコストより小さい)。

## 見送りの3条件(変更不可)

見送る場合、以下を全て書くこと。1つでも書けないなら見送らず走らせること。
  (a) 実測に基づく所要時間（推定なら、先にその推定を検証する）
  (b) CPU・提出枠・凍結済み予約と実際に競合している証拠
  (c) やらなかった場合のコスト
「締切が近い」「凍結前だから」は (a)(b)(c) のどれでもない。

※この3条件は制約される側(実行エージェント)が起草に関与しているため、
文言の緩和・例外節の追加・「ただし〜の場合は」の付与を**禁止**する(ゆうじ固定、2026-07-31)。

## 前進と検証は対である(reference.md の2記事)

前進の既定値は検証ゲートの撤去ではない。検証なしのループは「静かに失敗する自動化」
であり(Sonar)、停止条件は決定的な検査に置く。このプロジェクトの決定的ゲート =
台帳経由(T6)・事前登録・T7・CEW判定・robustness-guard。**ゲートは判定にかける、
測定にはかけない** — これが本スキルの一行要約。繰り返し手で行う検査はスキル化する(Claude blog)。

## 実例: 後回しの理由が3回連続で崩れた記録(2026-07-31、詳細は background.md)

| 後回しの理由(推定) | 実際 |
|---|---|
| 「①-a/②は8/13までに採択を変えないから測らない」 | 測ったら判定基準side(レポート証拠)で価値が確定し、被覆計数・着地一貫性55/56がwriteup素材になった |
| 「①-bはCPUが空かないから8/17以降」 | 実測見積50分。当日CPUは遊休。競合先とされた穴D予約(D55)は8/3のみ |
| 「エンジンソースはDLに人手が要る」 | kaggle CLIで45ファイル即時取得(D11-3: 7/2から公式公開の記録が既にあった)。writeupの断定誤り3件を即日検出 |

3件とも共通の機構: **後回しの理由が推定のまま検証されていなかった**。
関連する定量事実: 本番時間予算の実消費は最悪11.1秒/600秒=1.85%(D51-訂正の実テレメトリ。
D44の0.2%は対random由来で誤り) — 「資源が無い」系の推定は特に実測と乖離しやすい。
